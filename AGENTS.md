# CAD-Pilot Workbench

This repository owns reusable tooling and guidance, not every design project. Read README.md for commands and .agents/skills/README.md for the provenance policy.

- Do not hard-wrap prose to a fixed column width in our own READMEs or instruction files. Keep each paragraph or list item on one source line and let the editor wrap visually. Preserve code blocks and upstream formatting.
- Use relative paths in reusable documentation and examples. Derive the workbench location from the current checkout when needed; do not embed machine-specific drive letters or user directories.
- Keep first-party workbench content evergreen: describe maintained behavior and how to verify it, not session progress, one-off test counts, or dated success claims. Keep personal context in memory and project results with the project. Preserve provenance dates/revisions, licenses, and imported dependency locks; evergreen does not mean auto-updating imports.
- Apply YAGNI to additions: solve an observed workflow need before adding schemas, templates, integrations, or tracking machinery. At natural project handoffs, note useful outcomes or friction in existing project notes; revisit tooling when evidence warrants it. Lack of a usage record is not proof of non-use. Preserve user work when simplifying.
- Before importing any skill, instruction, prompt, or agent definition, add a provenance entry in the parent collection's README.md with source URL/path, immutable revision, import date, license/attribution, and local changes. Keep upstream READMEs and notices untouched; do not place workbench provenance files inside imported skill folders. Skills use .agents/skills/README.md.
- Keep pyproject.toml in version control and uv.lock local and Git-ignored. Use normal uv sync and uv run with each machine's configured feeds; do not require a committed Python lock or bypass required feeds. Python dependency versions can differ across machines.
- Apply the same local-lock policy to the first-party Explorer: commit explorer/package.json, but keep explorer/package-lock.json local and Git-ignored because its resolved URLs capture machine-specific feeds. Use normal npm install with each machine's configured registry; do not force a public registry or bypass required feeds. Versions allowed by the manifest can differ across machines. Keep imported npm locks version-controlled with their dependency versions and integrity hashes preserved; registry-metadata sanitization is a documented local patch, not a dependency update.
- Prepare source releases from tracked files, not an archive of the whole working directory. Local locks, caches and runtime data may contain machine-specific feeds or private project data.
- Work on the explicitly selected project. Run geometry generation from that project's directory with the workbench's local Python environment. Never write design output to the skill directory or edit unrelated project files.
- The project template is a proposed convention, not a mandatory structure. Use it for new projects unless another layout is preferred. For existing projects, respect their layout and instructions; do not reorganize or scaffold them merely to match the template. Locate their existing requirements, source, outputs, and review history before editing.
- Invoke the imported scripts/step and scripts/inspect launchers with the workbench's Python interpreter from the design root. Choose the project's artifact location with -o, using a project-relative forward-slash STEP path for both generation and inspection. STL/3MF sidecar paths are relative to the STEP directory. Do not impose outputs/, brief.md, or .cad-pilot.local.json on existing projects; use their own layout and the explicitly supplied workbench path. See README.md for direct commands, including Explorer startup with explicit project roots.
- Use the cad skill for build123d generation and geometric inspection. Use the visual-review skill for choosing/opening a viewer, design discussion and feedback.
- Prefer the maintained `cad-explorer` canvas whenever it is available in the current host. This viewer choice takes precedence over the imported cad skill's browser-startup guidance, not its modeling or Python inspection guidance. Discover the canvas capabilities, then open the actual STEP with an explicit `projectRoot` and `file`; do not substitute the demo. Reuse the existing panel for the same setup. See `explorer/README.md` for build/open commands.
- If the `cad-explorer` canvas is unavailable in the current host, use the imported browser viewer and its CLI inspection workflow. Do not silently switch viewers to hide a failed maintained-canvas build or connection; report that problem first. Project-scoped canvas availability is not implied by access to the workbench files, and a separate VS Code extension is not implemented.
- Resolve maintained-viewer `cadproto:v2` references or their JSON descriptors with `cad_explorer_inspect` or the canvas's `inspect_reference` action. `cad_explorer_prototype_inspect` is a compatibility alias, not a reason to reopen the archived prototype. Resolve imported `@cad[...]` references with the imported inspector. Never mix the two face/edge-numbering systems.
- Use the fdm-design skill before modeling or revising FDM/FFF prints, choosing orientation/material, or evaluating fit and print preparation. Treat it as guidance, not an automated printability gate; keep manufacturer limits, provisional design choices, and measured calibration separate.
- Describe objects in plain language. Ask about purpose and physical dimensions, not CAD terminology. Show rough alternatives before detailed finishing.
- Python source and named parameters own design intent. STEP and mesh exports are derived artifacts. Do not claim a STEP file preserves parametric history.
- Critical dimensions, fit, material, printer, and nozzle are unknown until confirmed. Upstream default dimensions and clearance values are proposals, not measured printer calibration or user requirements.
- Validate generated geometry, not just parameter constants. Distinguish kernel validity, measured requirements, visual review, slicer checks, and physical testing. Never label an unchecked requirement as passed.
- Treat screenshots and geometry selections as revision-specific. Confirm the highlighted target before an ambiguous edit; preserve unaffected dimensions.
- Do not send G-code to a printer or publish models without explicit approval.
- Do not change global Git identity, switch GitHub accounts, commit, or push unless requested. This checkout uses a repository-local personal identity.
- Use tools/gh-personal.ps1 for GitHub CLI operations on CAD-Pilot, and its -Git switch for authenticated Git operations such as push. It scopes personal credentials to that process without switching global accounts. Bare gh or Git credential helpers may otherwise use the work account.
